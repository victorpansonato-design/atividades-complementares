# Decisões provisórias e pendências para o TI

Nada aqui impede apresentar o front. Tudo precisa ser confirmado antes de tratar o protótipo como sistema institucional. As escolhas estão **configuráveis**
(`policies` em `StudentContext`) ou isoladas no adapter mock.

| Tema                            | O que o protótipo faz hoje                                                                                                | O que precisa ser definido                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Autenticação                    | Sessão de **aluno fictício** (`MockSessionProvider`). Sem SSO, cookie ou `/funcionarios/me`                               | Auth real do aluno no portal, contexto de matrícula, retorno seguro, tratamento de 401                    |
| Catálogo por matrícula          | Perfil aponta para o catálogo 2025 ou um catálogo legado mockado                                                          | IDs oficiais de catálogo/tipo, vigência por curso/matriz, elegibilidade                                   |
| Variantes e teto                | Cada linha/subtipo tem orçamento próprio (`budgetKey`)                                                                    | Chave oficial de saldo; variantes compartilham teto?                                                      |
| Reserva em pendência            | `precisa_correcao` reserva (`pendingCorrectionReserves`)                                                                  | Quais estados reservam e quando liberam                                                                   |
| Reconsideração                  | Mesmo protocolo, 1 tentativa (`reconsiderationMaxAttempts`), reserva **o valor solicitado** uma vez; documentos opcionais | Protocolo próprio ou filho? Valor reservado (ex.: pedido acima do limite atual)? Nº de tentativas         |
| Limite semestral                | Agrega tipo/subtipo + período; dividir em protocolos não cria saldo                                                       | Períodos oficiais; atividades que cruzam períodos                                                         |
| Uso único (25_024, 25_028)      | Pedido ativo ou aprovado bloqueia; recusa libera nova tentativa (`oneTimeRejectedAllowsRetry`)                            | Escopo (matrícula/curso/aluno) e retry após recusa                                                        |
| Atribuição fixa com saldo menor | Permite pedir até o saldo, com aviso (`partialCreditForFixedAssignment`)                                                  | Crédito parcial é aceito?                                                                                 |
| Atividade anterior ao ingresso  | Aviso em tipos gerais (`preAdmissionActivities: "warn"`); aproveitamentos isentos                                         | Bloquear? O §5º do art. 4º citado no PDF não existe no texto                                              |
| Código 25_030                   | Só histórico, sem teto nem envio                                                                                          | Nome, documentos, teto, regra de registro                                                                 |
| Códigos legados                 | Limites observados no print, sem migração                                                                                 | Conversão e política de novos envios para matrizes antigas (o catálogo legado fica **sem envio** no mock) |
| Prazo de análise                | Texto "até 30 dias úteis", sem data calculada                                                                             | Calendário de dias úteis, início da contagem, suspensão em pendência                                      |
| Prazo de entrega (concluinte)   | Data vem do perfil (fictícia no cenário); limita prazos de correção/reconsideração                                        | Calendário institucional; enquadramento do **híbrido** (`hybridConclusionPolicy` vazio → aviso)           |
| Semestre subsequente            | Prazos de pendência/reconsideração vêm do pedido (fictícios); decisão simulada usa o fim do próximo período mockado       | Prazo retornado por pedido                                                                                |
| Período acadêmico               | Sugerido pelas datas só para presencial (`suggestPeriodFromDates`); aluno confirma                                        | Calendário EAD/híbrido; distribuição entre períodos                                                       |
| Upload                          | PDF/DOC/DOCX; extensão + MIME + assinatura do arquivo; 10 MB e 10 arquivos **como demo**                                  | Limites reais, armazenamento, antivírus, download autenticado, formatos futuros                           |
| Representante (25_026)          | Requisito cumprido por cadastro institucional (estado simulado "confirmado")                                              | Como consultar o cadastro sem exigir documento do aluno                                                   |
| Total do curso concluído        | Sem bloqueio global (`allowNewRequestsAfterCompletion`)                                                                   | Política após cumprir a carga                                                                             |
| Descrição legada                | Nome + organizador + detalhes serializados, até 6.000 caracteres                                                          | Campos estruturados aceitos pelo backend                                                                  |
| Evento institucional ausente    | Ajuda orienta a aguardar o prazo e não reenviar                                                                           | EventId, conciliação, duplicidade, canal de contestação                                                   |
| Concorrência                    | Revisão de saldo + idempotência por chave no mock (uma aba)                                                               | Transação e autoridade no backend                                                                         |

O front deve consumir catálogo, saldos e prazos **calculados pelo backend**. As regras locais (`rules/`) existem para o protótipo e para prevenir erros de
preenchimento; não são barreira institucional única.
